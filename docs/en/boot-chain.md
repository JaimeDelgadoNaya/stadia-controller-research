# Boot chain and update validation — phase 9

[Español](../es/arranque.md)

This analysis refers only to bootloader build **169429**, SHA-256
`59ebfd2c156075e498ecf318984cb297750c9c5b7cb321b0ea97edee315f2ca0`, mapped
at `0x60800000`. Function labels below are research descriptions, not recovered
source symbols. Instruction ranges are generated by `tools/analyze_bootloader.py`.

## Application handoff is gated by validation

At `0x60801EF0`, the handoff routine selects an application address and calls the
validator at `0x6080200C` from `0x60801F00`. A nonzero low-byte result takes an
error path and returns. Only the success path loads the initial stack pointer
and reset handler, disables interrupts, changes the vector-table pointer and
branches to the application's reset handler at `0x60801F46`.

The validator checks the application slot base, vector-table ranges and metadata
pointers before calling the HAB wrapper at `0x60801F5C`. A second direct caller
of the application validator was observed at `0x60802838`; its entire surrounding
dispatch path has not yet been reconstructed.

## The HAB wrapper

`0x60801F5C` calls `entry` through `0x00200304`, requires HAB Success (`0xF0`),
calls `authenticate_image_no_dcd` through `0x0020032C`, then calls `exit` through
`0x00200308`. It compares the returned image entry address with the expected
address. The RVT layout is defined by NXP's [reference implementation](https://github.com/nxp-mcuxpresso/sbl/blob/master/component/secure/semifunc/hab_rvt.c).

For an application whose metadata IVT pointer is zero, the validator has a
separate path. If the shared boot IVT contains a CSF pointer, this path calls
`report_status` through `0x00200324` and requires both successful status and HAB
configuration Open (`0xF0`). The measured Closed configuration is not Open.
The separate branch for a shared IVT with a zero CSF pointer has not been
dynamically exercised and is not evidence that an attacker can change that
signed boot structure.

## Update validation has a structural-only mode

The routine at `0x608020A8` accepts a flag in `r1`:

| Call site | Flag observed | Interpretation supported by the instructions |
|---|---:|---|
| `0x60801E02` | 1 | Checks the current bootloader using the authentication-enabled path |
| `0x60801E28` | 0 | Candidate pre-validation uses the structural-only path |
| `0x60801E84` | 1 | Validation after the intervening update operations enables authentication |

At the second call, `r1` is zero because it holds the successful status from the
first call, via `UXTB r1, r0` and the zero branch. At `0x60802154`, a zero flag
returns after structural checks; a nonzero flag tail-calls the HAB wrapper from
`0x60802168`. Thus a pre-validation success must not be reported as proof that
cryptographic verification already happened. The intervening indirect calls and
the complete update/rollback state machine remain subjects for further analysis.
No update operation was run on the device during this phase.

## Arithmetic observation: not a demonstrated vulnerability

The range helper at `0x60801FE6` checks that `start` and the 32-bit computed
`end = start + size - 1` are individually inside the allowed interval. It does
not explicitly require that the addition did not wrap or that `end >= start`.

An offline arithmetic witness is:

```text
lower = 0x60000000; upper = 0x60FFFFFF
start = 0x60000010; size = 0xFFFFFFF8
computed end (uint32) = 0x60000007
observed helper model: accept
nonwrapping interval model: reject
```

Three direct calls to this helper were traced at `0x608020FA`, `0x6080211C` and
`0x60802138`. The first two use fixed length `0x10`; the third obtains a length
from boot-data metadata. This is a reason to inspect the metadata flow, not a
claim that the witness reaches a useful operation. Authentication-enabled
validation still reaches HAB afterward. No signature bypass, arbitrary write,
code execution or device-level impact has been demonstrated.

Run `python tools/model_ranges.py` to reproduce the arithmetic only.

## What this changes

The research now has an extracted, signature-checked permanent bootloader and
specific control-flow evidence. It rules out treating the structural-only flag,
an unsigned-image branch or the word “dev” as an established firmware unlock.
The next work is to reconstruct the metadata, update callbacks and fallback
selection before proposing any device experiment.
